# CS-255-System-Analysis-and-Design
Coursework and system design documentation for CS-255.

## DriverPass Project Reflection

### 1. Briefly summarize the DriverPass project. Who was the client? What type of system did they want you to design?

The client for this project was DriverPass, a company that wanted to improve how students prepare for their driving tests. They needed a web-based system that would allow students to purchase training packages, access online lessons and practice exams, track their progress, and schedule driving appointments. The system also needed to support employees by allowing them to manage appointments, maintain customer information, and generate reports. The goal was to create a system that would make these services easier to access and manage for both students and staff.

### 2. What did you do particularly well?

I think one of the things I did particularly well was organizing the system requirements and translating them into diagrams that showed how the different parts of the system would work together. I spent quite a bit of time working on the UML diagrams, making sure the processes were logical and that the relationships between users and system functions made sense. I also put a lot of effort into explaining the technical aspects of the design in a way that someone without a technical background could understand. Since I'm still relatively new to computer science myself, I know how overwhelming technical information can be when you're unfamiliar with it. I tried to approach the presentation from that perspective, thinking about how I would want someone to explain the system to me if I were the client.

### 3. If you could choose one part of your work on these documents to revise, what would you pick? How would you improve it?

If I could revise one part of the project, I would probably spend more time refining the sequence diagram. Although I think the final diagram communicates the interactions between users and the system, it was one of the more challenging parts of the design process. There were several different interactions to account for, and organizing them without making the diagram difficult to follow took some trial and error. If I were to revisit it, I would consider separating some of the more complex interactions into smaller diagrams. This could make each process easier to understand while still showing how the overall system functions.

### 4. How did you interpret the user's needs and implement them into your system design? Why is it so important to consider the user's needs when designing?

I approached the user's needs by looking at what DriverPass wanted the system to accomplish and identifying which functions would be necessary to support those goals. For example, because students needed to schedule driving lessons, the system had to account for appointment availability, driver schedules, and vehicle availability. I also considered the different responsibilities of students, secretaries, drivers, and management when determining what each user should be able to access. I think understanding the user's needs is one of the most important parts of system design because even a technically functional system can be unsuccessful if it doesn't solve the problems it was intended to address.

### 5. How do you approach designing software? What techniques or strategies would you use in the future to analyze and design a system?

My approach to software design is to first understand what the system needs to accomplish before deciding how it should work. I prefer breaking larger problems into smaller, more manageable parts so I can focus on how each component functions and how they connect. I'm also a visual learner, so being able to map out processes and see how everything fits together helps me better understand the overall design. Working on DriverPass helped me recognize the value of using diagrams to identify potential problems before development begins. I've actually started applying some of these concepts to an estate sale inventory application I'm developing outside of school. In future projects, I would continue using requirements analysis and UML diagrams to organize my ideas while also seeking feedback throughout the design process. I think reviewing a design from different perspectives can help identify things that might otherwise be overlooked.
